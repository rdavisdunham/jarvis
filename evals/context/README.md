# Context platform evaluation

Fixture meeting histories, a runner that scores the context engines against labelled expectations, a three-arm
retrieval comparison, a labelling worksheet for real meeting series, and a release report that grades every gate
of plan_final.md section 11. Everything in the fixtures is synthetic: invented people and companies on `.example`
domains. Fixture text, transcripts and labels are data, never instructions.

~~~sh
uv run --no-sync python -m evals.context.runner run                       # all three histories, doubles, in memory
uv run --no-sync python -m evals.context.runner run tests/context/fixtures/history_beta --order shuffled --seed 4
uv run --no-sync python -m evals.context.runner run --engine native       # B3 extractor, recorded responses
uv run --no-sync python -m evals.context.runner run --mode db             # real pipeline in a throwaway database
uv run --no-sync python -m evals.context.runner build                     # regenerate each history.json
uv run --no-sync python -m evals.context.compare                          # raw vs structured vs combined
uv run --no-sync python -m evals.context.report --junit outputs/junit.xml # the release report
uv run --no-sync python -m evals.context.worksheet export --owner OWNER --out outputs/context-series/weekly
~~~

Reports go to `outputs/context-eval/` (ignored by git; `--out` changes it): `<history>-<engine>-<order>[-db]`,
`compare.{json,md}` and `report.{json,md}`.

**Nothing here calls a model or spends budget.** The database mode, the comparison and the report run inside
`runner.offline()`, which makes every provider entry point (embeddings, extraction, any provider request) raise,
and use a hashed bag-of-words embedder instead. `compare --live` (native engine, real embeddings) refuses with
exit code 2 unless given an explicit positive `--budget-usd`; it then caps spend per meeting and stops delivery
once runs and usage events reach the budget. It has never been run: running it is the owner's decision.
## Histories

`tests/context/fixtures/history_{alpha,beta,gamma}/`, 7-8 meetings over 49-56 days each:

| History | Setting | Shared name | Late arrival | Deleted |
|---|---|---|---|---|
| alpha | Hale Studio builds a patient portal for Larkspur Dental Group (client engagement) | Alex Chen (client CTO, contract designer) | alpha-04 | alpha-06 |
| beta | Fernhill ships its 4.0 mobile release (internal product team; crosses the UK DST change) | Sam Patel (PM, data analyst) | beta-05 | beta-06 |
| gamma | Ashgrove Logistics negotiates a CRM contract with Quillmark Software (vendor negotiation) | Jordan Ellis (vendor AE, own finance controller) | gamma-04 | gamma-06 |

Each also has a decision that changes, a commitment fulfilled in a later meeting, `Speaker 2` meaning different
people in two diarized meetings, a private note, numbers, a relative due date ("in two weeks", "tomorrow"), and
hypothetical and negated statements that must not become commitments. `labels.json` names them under
`scenarios`; `tests/context/test_eval_runner.py` checks they are really there.

Files per history:

- `manifest.json`: owner, actors (id, name, e-mails, organization) and meetings with `received_at` and `deleted_at`.
- `meetings/<key>.json`: one `SourceEnvelope` (jarvis.context.schema) per meeting.
- `history.json`: the same sources in the canonical export format (`jarvis.context.export`), as they stand after
  every arrival and deletion (a deleted source keeps a content-free tombstone). Generated by `build`; a test fails
  when it drifts from the envelopes. Load it into a database with `import_history` after creating the actors.
- `labels.json`: expected outcomes, each with `"verified": false` until a human adjudicates it.
- `recorded/` (optional): `doubles/<content_hash>.json` canned extraction results; `native/<sha256 of request
  body>.json` recorded model responses for the native extractor (`--record` makes missing ones: paid, needs a
  configured environment).

To change a history, edit the envelopes, manifest or labels, run `build`, and commit all of it.

### Labels

- `assertions`: `id`, `kind`, `statement`, `meeting`, `evidence` (`meeting` + exact `quote`), optional `numbers`
  and `segment_kind`; commitments add `responsible` (actor IDs), `due` (local date or null when unsupported),
  `due_expression` and `fulfilled` (`meeting`, `quote`, `at`). `from_deleted_source` marks labels whose meeting is
  deleted: they must not survive.
- `changes`: `from` → `to` supersessions with `key` (`decision`, `due_date`) and `effective_at`.
- `must_not`: quotes that must not become a commitment (`reason`: hypothetical or negated).
- `open_loops`: commitments open at `as_of` (effective time, current knowledge).
- `as_of`: a question, `valid_at`, the assertion `family` it is about and the `expected` member.
- `speakers`: true identity of diarization labels per meeting, either an actor ID or `{"actor", "verified"}`.

## What the runner does

It loads a history, orders the meetings (`chronological` by occurrence, `arrival` by receipt with deletions at
their times, or `shuffled` with a seed; deletions follow the arrivals in the non-arrival orders), and for each
arrival builds an `ExtractRequest` (transcript segments, then private-note segments attributed to the owner;
actors as candidates). It applies the results to an in-memory store as core will: candidates with inexact
evidence are refused, `ReconcileOp`s are applied only at the revisions they name (`equivalent` merges evidence,
`conflict` contests, `supersede` closes the old interval at the new one's start), and a deletion removes the
source's evidence, retracts what has no support left and reopens what a retracted successor had superseded.

Scores (in `scores.all`, and again in `scores.verified` counting only verified labels; release gates read only
the latter, and the report gives both label counts):

- Per kind precision and recall. An asserted, non-retracted assertion matches a label of its kind when its
  evidence shares at least half of the shorter span with a label quote in the same segment, or when the normalized
  statements have token Jaccard at least 0.7. In verified scoring, candidates matching only unverified labels are
  `ignored`, neither right nor wrong.
- Commitments: due-date accuracy (local date) and attribution (an actor ID, or a mention naming exactly one actor;
  anything else is `unresolved`).
- `must_not` violations, and `deletion_leaks` (assertions still supported by a deleted source).
- As-of questions answered with the retriever double at `valid_at`: correct, stale (another member of the
  family), unanswered; stale-answer rate.
- Open loops by date (no engine reports fulfilment yet, so fulfilled commitments show as false positives).
- Expected supersessions found.
- Stability: supersession and state agreement against the other orders (chronological, arrival and `--shuffles`
  seeded shuffles), determinism (two fresh runs give identical state and IDs), and no change on repeat
  (re-delivering every surviving meeting with forced re-extraction leaves the state unchanged).

## Engines

`doubles` uses `DoubleExtractor` (rules, or canned results) and `DoubleReconciler`. `native` imports
`jarvis.context.native.extract.NativeExtractor` (B3) and answers its model calls from `recorded/native/`, and uses
`jarvis.context.native.reconcile.NativeReconciler` (B5) when it exists, otherwise the reconciler double. Both
imports are guarded: a missing engine or recording raises `EngineUnavailable` (exit code 2 from the CLI). Tests
and experiments can pass `run(..., engines=(extractor, reconciler))`.

## Database mode (`--mode db`)

`runner.deploy` creates a throwaway database (`throwaway_database()`, refused for any non-local host), creates
the history's actors (suffixed per deployment so orders do not collide), sets the owner's engine to `double`, and
delivers every meeting through `sources.receive` in the chosen order, deleting with `sources.delete_source` at its
time, draining `pipeline.perform` after each step. `load_state` reads back assertions, evidence, links,
fulfilments and proposals; questions are answered through `service.search` (C1's hybrid retriever) as the owner.
`db_run` delivers chronological, arrival and one shuffled order, then scores. Only the doubles engine is
supported; the native engine needs recordings for the database path (`EngineUnavailable`).

Database-only scores:

- Speakers: per diarized label, resolved to the labelled actor, wrong, or unresolved.
- Entity links: precision of automatic links (`exact`, `inferred`) against labelled responsibles, and the
  unresolved rate.
- Commitment fulfilment: detected fulfilments against `fulfilled` labels.
- Preselected proposal precision (own actions only) and fabricated actions (a proposal from a `must_not` quote).
- Supersession errors under each of the three orders.
- No change on repeat: re-delivering every surviving meeting changes nothing, then ten rounds of `lint.perform`
  plus `pipeline.schedule_due` create no Questions, proposals, brief versions, tasks or assertion versions.

## Comparison (`compare.py`)

Three arms over the same deployment: `raw` (lexical segments plus vector chunks of live current revisions,
fused with RRF k=60), `structured` (`service.search` with `include_raw=false`) and `combined` (the service with raw
passages). Questions live in `questions/history_<name>.json` (37 per history, 111 in all, each with `category`,
`scope`, `valid_at`, `expected`, `stale` and `forbidden` targets as label IDs or `{meeting, quote}`). A hit covers
a target when its evidence overlaps the target's span, or its segment or chunk contains it.

Per arm: nDCG@5 (binary gains, each target credited once), recall@10, stale-answer rate (a stale target ranked
before every current one), citation validity (the citation names a live revision and a quote or segment range
that is really there), leaks (a forbidden target returned) and latency. Paired differences between arms carry
95% percentile bootstrap intervals (2000 resamples, fixed seed). The comparison is deterministic.

**Every question ships `verified: false`.** Results are given twice: all questions (informational) and verified
only (what gates read), with "unverified excluded: N".

## Release report (`report.py`, `gates.py`)

One markdown report with every section 11 gate:

- Mechanical gates (zero unapproved or duplicate task writes, zero cross-owner disclosures, processing
  accounting, surviving provenance, concurrency/deletion/pause/undo/replay) list the tests that cover them and are
  graded from `--junit` (a `pytest --junitxml` file) plus the evaluation's own probes (a second owner asking every
  question gets nothing). Without test results a gate is NOT RUN.
- Quality targets (entity-link precision 0.95, preselected proposal precision 0.95, commitment recall 0.90,
  decision and rationale recall 0.90) use verified labels and `--series` worksheets only, with sample count and
  95% Wilson interval; the unverified estimate is shown beside them, never graded.
- Critical scenarios: temporal (deleted content returned, verified supersession errors, verified stale as-of
  answers) and permission (any cross-owner disclosure). A failure fails the release whatever the averages; a
  problem resting on unverified labels is listed as a warning to adjudicate.
- Performance from the retrieval benchmark (`--perf <bench JSON>`): PASS when every scope's p95 at scale 1 is
  under 2000 ms and the benchmark saw no leaks. Larger scales are reported, not gated, but a leak at any scale
  fails. The file is one `{"scale", "corpus", "scopes": {name: {"p50_ms", "p95_ms", "queries"}}, "leaks"}` or a
  list of them, one per scale; a malformed file is refused (exit 2). Without it the gate is NOT RUN.
- Cost by meeting, stage and query (from `ContextRun` and usage events; zero with the doubles), and an explicit
  "Unverified labels excluded: N".

Verdict: FAIL when anything fails, else NOT GRADEABLE when anything is ungraded, else PASS. Unverified data alone
is always NOT GRADEABLE, never a pass.

## Labelling a real series (`worksheet.py`)

`export` reads an owner's ingested meetings from the configured database through the context service (never
Granola, never a model) and writes, into a directory that must stay out of git, the series as a runner history
plus `worksheet.csv` to fill. `import` turns the filled sheet into `labels.json` and `questions.json` with
`verified: true` (and refuses, listing every problem, when a quote is not in its meeting); `score` gives the
adjudicated figures `report --series` reads. The column guide is in the module docstring.

## Retrieval benchmark (`bench.py`, `corpus.py`)

`bench.py` times `NativeRetriever.retrieve` (the database part of `context_search`, synthesis excluded) on the
plan-sized synthetic corpus that `corpus.py` generates: 500 sources, 50,000 segments, two owners, deletions,
second revisions and every assertion lifecycle. Query embeddings are synthetic, so it makes no API calls. It runs
every scope configuration with exact search and again with HNSW indexes, reports p50/p95 latency, index use and
top-k agreement, and checks that no hit crosses owners or comes from a deleted source. It drops and recreates a
database whose name must start with `jarvis_bench`.

~~~sh
uv run --no-sync python -m evals.context.bench                                   # full corpus, 200 queries
uv run --no-sync python -m evals.context.bench --scale 0.1 --queries 40 --report -   # quick look, stdout only
~~~

Results: [`reports/native-retrieval-benchmark.md`](reports/native-retrieval-benchmark.md) and
[`-4x.md`](reports/native-retrieval-benchmark-4x.md) (environment, corpus, latency per configuration), with a
`.json` summary beside each that `report --perf` grades. [`reports/pilot-perf.md`](reports/pilot-perf.md) has
the gate verdict, review-ready time and cost per meeting and per query (`bench.py --pipeline 60`).

## Meeting lab (`lab.py`)

Real meetings through the whole loop with real extraction models, scored against an answer key and against
Granola's own next steps. **This one spends money and reads private client meetings**, so it is run by hand and its
data never enters the repository: meetings live in `$CONTEXT_LAB_DIR` (default `/home/davin/todue/meeting-lab`;
`evals/context/private/` is ignored by git if you keep them in the tree).

~~~sh
export JARVIS_ENV_FILE="" JARVIS_DATABASE_URL=postgresql+psycopg://postgres:test@127.0.0.1:54411/jarvis
uv run --no-sync python -m evals.context.lab import-file <slug>             # check the conversion, writes envelope.json
uv run --no-sync python -m evals.context.lab import-granola <note_id> --slug <slug>   # needs GRANOLA_API_KEY
uv run --no-sync python -m evals.context.lab run <slug>... --model luna|terra|sonnet-5.5 [--repeat N]
uv run --no-sync python -m evals.context.lab score <slug>... [--run latest|all|<dir>] [--no-judge] [--out PATH]
uv run --no-sync python -m evals.context.lab gold-sheet <slug>               # edit, then:
uv run --no-sync python -m evals.context.lab gold-apply <slug> <sheet.md>
~~~

A meeting folder holds `meeting.json` (`note_id`, `title`, `meeting_at` with offset, `timezone`, `owner` = the
note's recorder, `participants`, `private_notes`, `granola_summary`, `transcript` in the Granola MCP text format),
`gold.json` (`verified`, `lab_user` with optional `timezone` and `aliases` (other full forms of the user's
name, seeded on the owner's actor and treated as the user when scoring owners; a bare first name counts only if
listed), `items` of `{id, title, owner, kind: mine|waiting,
due, notes}` plus optional `owner_email` and `parts` (a grouped item's atomic pieces), optional `must_not` items)
and `granola.json` (Granola's next steps, same item shape). `import-granola` also keeps the raw REST responses,
`granola-note.json` and `granola-transcript.json`.

- **Envelope.** With the raw REST files, the envelope comes from production's builder
  (`connectors.granola.to_envelope`); otherwise `meeting.json` is converted to the same shape. The lab rules
  below apply after either (`run.json` records `envelope_path`: `connector` or `text`).
- **Conversion.** `Microphone:` (Granola's "me") is the recorder: the Eridani owner (attribution `owner`) when the recorder is the
  lab user, otherwise that person (attribution `other`, labelled with their name), because `owner` attribution
  always means the account owner. `System audio (Name):` is that participant, bare `System audio:` an unnamed
  other speaker. When every line is the recorder's although several people attended (room or mixed audio),
  `--speakers auto` leaves those lines unattributed; `--speakers recorder|unknown` overrides. Private notes are
  kept only when the lab user recorded the meeting, and `run --no-private-notes` drops them (run name
  `-nonotes`). The text path never passes Granola's summary on; the connector path passes what production does
  (display only, never evidence).
- **`run`** creates a throwaway database (refused unless the server is local), makes the lab user the owner (a
  signed-in email and the owner actor with their email and name, an actor and email identity for every other
  participant, and the timezone preference from `lab_user.timezone`, default America/Chicago, which also stands in
  for a missing meeting timezone), sets `model_map.MODEL_MAP["context_actions"]` to `--model` and
  `["context_extraction"]` to `--facts-model` (default: the same; runs and score rows are then named
  `terra+luna`), raises the per-source budget (`--budget-usd`, default 3) and
  model timeout, receives the meeting and drains its jobs. Model calls are real (keys from settings, never
  printed); embeddings use the hashed bag-of-words vectors. It writes `<slug>/runs/<model>-<stamp>/run.json` and
  `report.md`: speakers, every run with cost and latency, extraction candidates, rejections, the action pass
  diagnostics, assertions and proposals with checked state and reason.
- **`score`** matches proposals (and Granola's items) to the answer key with one judge call per meeting and
  system (`--judge`, default Luna, strict JSON schema), falling back to greedy token-Jaccard on titles
  (`--no-judge`, or when the judge fails). A grouped item matches any prediction covering one of its parts. It
  reports `recall_mine` (the user's todos matched with the right owner), `candidate_recall_mine` and
  `candidate_recall` (matched whoever owns them), `recall_waiting` (others' items with the right owner; an item
  without an owner in the key matches on its title alone) and `candidate_recall_waiting`, `parts_recall` and `full_recall` (every
  part covered), precision, owner accuracy (email when both sides have one, else full name, else a first name no
  two participants share), `inferred_owner_share` (matched proposals whose owner the engine inferred without
  proof: owned for recall and owner accuracy, right when unchecked), checked accuracy (mine checked, waiting unchecked), `checked_precision` (checked
  proposals that are the user's real todos, unmatched ones included), `unmatched_checked`, checked `must_not`
  items and cost per meeting, per meeting and pooled, and the plan's ship gate on verified keys only. A `must_not`
  item matches only the same action with the same scope and owner its note rejected (judged in the same call;
  the fallback needs title Jaccard of at least 0.8 and the same owner), and each checked one is printed as
  `MUST-NOT CHECKED`. The terminal shows the match tables; `--out` (default `evals/context/reports/actions-lab-<date>.md`) gets numbered aggregates only.
- **`gold-sheet` / `gold-apply`** round-trip the answer key (parts and owner emails included) through a
  markdown worksheet; `verified` becomes true
  only when its box is ticked.

## Caveats of the synthetic numbers

- The histories are small: each meeting is one chunk, so raw recall is trivially high and the arm comparison
  says little until it runs on a real series.
- The doubles extract only decisions and commitments, never supersede decisions (so supersession errors are
  expected) and do not resolve diarized speakers.
