## Cost per query

Database time only here. In production each `context_search` adds one query embedding (`text-embedding-3-small`, about 4 tokens for these queries): roughly $0.0000001 at an assumed $0.02 per million tokens, recorded under cost feature `context_embeddings`. No other model call is made before synthesis.

## Recommendation

**HNSW recommendation: not needed.** Exact cosine scan meets the gate at corpus size (worst p95 530 ms < 2,000 ms); keep it and rerun this benchmark before adding an index. With HNSW indexes present the planner still chose the exact plan for every configuration: the semantic leg orders by `distance, id`, which an HNSW index cannot serve, and the owner and lifecycle filters leave few enough rows that a sort is cheap. An index-friendly leg (distance only, index forced) would take the bare semantic leg from p95 11.7 ms to 4.1 ms at recall@100 98.1%; revisit when the exact leg approaches the budget, and then drop the `id` tie-break from the ORDER BY (keep it only as a post-sort).

## Headroom at 4x (added by hand from a partial run)

`--scale 4` on the same machine (2,000 sources, 200,000 segments, 11,054 chunks, 28,946 assertions; owner A holds
60%) completed the exact-scan phase before its HNSW build failed on Docker's 64 MB `/dev/shm` (since fixed: the
build is now serial). Exact p50/p95 in ms: owner 139/178, owner+raw 311/380, entity 140/171, entity+raw
1,471/2,706, known_at 296/452. Only `entity+raw` exceeds the 2 s gate, and it is the configuration whose cost is
not vector search (see the slowest-configuration note above). So the first scaling fix is the raw-hit entity scope
(`_segment_matches_entities` and the stale-passage check over segments), not an ANN index.
